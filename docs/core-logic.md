## 架构总览（两个循环一个切面）

- **拼图**与**执行**各自有清晰的输入、主干步骤与产物；**一方不能替代另一方的职责**。
- **拼图**是否在进行**与是否正在跑某条执行任务**无关：可**错开、异步**运转。
- **执行**只有在拼图侧认定**里程碑有效**且**先决条件已全部满足**（门控一致）后才能进入。
- **迭代切面**贴在「拼图循环」「执行循环」与**每次 Session 边界**上：失败走推理/审计与反馈；成功沉淀资产与排行榜；**知识蒸馏**在失败与成功路径之外**横贯**执行结果，写入可追溯存储供下一轮使用（与 `docs/procedure/distillation`、`docs/sessions` 等约定对齐）。

以下为**拼图循环、执行循环与迭代切面**在文档与消息层面的**依赖方向**（**不是**两条互不相干的闭环：切面会触及两侧；执行**仅当**门控从拼图侧就绪后才应启动）。

## 拼图环节（循环）

### 定义

**拼图环节**把用户的原始表达，经理解与拆解，变成**可门控的里程碑**与**先决条件（Prerequisites）**，并在「当前能力与条件是否足以满足门控」的意义上持续澄清与修正。它回答的是**做什么、分几步算做完、缺什么才能开始做**，而不是「这一轮编码/交付进行到第几步」。**本环节不出现 `session_id`**（理由见执行环节中的子节）。

### 输入

- 用户原始需求、对话与上下文。
- 由其它入口汇入的、可写入需求/反馈语境的材料。

### 激活与触发

- **异步激活**：不假设「执行环正在运行」或「任务空闲」。
- **触发器**：存在可**形成新需求或收窄歧义**的**有效反馈**时，唤醒拼图侧编排（与 [backend-modules.md](./product/backend-modules.md) 中「反馈与触发器」模块表述一致）。

### 本项目的核心执行逻辑

**主干（一轮拼图循环内推荐顺序）**

1. **需求分析与拆解**
2. **里程碑创建**（含「做到哪一步算过关」的语义）
3. **各里程碑先决条件分析**
4. **标出当前不满足的条件（Unsatisfied）** 与缺口、歧义
5. **蒸馏**：将缺口、歧义与依赖整理为**结构化反馈**
6. **用户侧对话**，再次明确需求；**可反复多轮**直至文档层面的里程碑与先决条件**收敛**

与仓库文档习惯的对应关系（非替代关系）：需求包、里程碑、`prerequisites`、Satisfied/Unsatisfied、反馈回路，均落在拼图语义下。

**与执行的交接条件（硬性）**

- 里程碑被认定为**有效**；且
- **其先决条件已全部满足**（门控状态与文档一致）。

**否则**不得进入执行环节；应在拼图内继续演进或回流需求。

**闭环（与执行任务的关系）**

拼图可**异步**、**多次**被触发；**不与执行任务对齐**。不可行时不得强行进入交付主干；仅当上述交接条件满足时，才移交执行。

## 执行环节（循环）

### 定义

**执行环节**在**拼图已裁定门控就绪**之后，为**交付可验收产物**而组织：准备、任务与工作流、按规范步骤实现与验证、**检查 → 合并 → 构建 → 清理**的交付流水线，直至对用户可见的产出落地并结案。

### 前置条件（来自拼图）

**必须**同时满足：**里程碑有效**；**所有先决条件已满足**；文档与门控状态一致。不满足则**仍处于拼图环节**，不得启动本环节主干。

### `session_id`（执行环节 · 子概念）

进入执行环节后，需将**同一轮**从「开工」到「结案」之间的任务、工作流状态、产物与记录**串成可证明的线索**。因此在本环节引入 **`session_id`**：**在门控已通过、本轮执行被承认时**建立（或选定）**唯一**主键，写入任务/工作流元数据、文首字段及与本轮绑定的路径或日志。**拼图既不分配也不消费 `session_id`**。权威定义、按时间顺序的环节表与字面值规范见 [sessions.md](./sessions/sessions.md)、[documentation-standards.md](./documentation-standards.md) 规则 3.1。

### 本项目的核心执行逻辑

**主干（严格先后顺序）**

1. **承接门控并登记主键**：确认前置条件已满足；按约定生成本 **`session_id`** 并写入元数据。
2. **准备（Preparation）**：物料、环境、权限与文档就绪（与 `docs/procedure/preparation` 等约定对齐）。
3. **任务分发（Dispatch）**：在**混合智能体决策与人机协同**策略下拆出 **Task** 集合。
4. **任务形态（强制）**：拆任务时**必须显式**选择 **并行执行** 或 **串行执行**（策略应可落库、可审计）。
   - **并行**：配备**监督器（Supervisor）**；出现**冲突**时**必须**走 **智能体建议 + 人工决断**，不得自动静默合并冲突。
   - **串行**：形成**任务队列**按序执行，**尽可能降低资源损耗**（排队、背压、暂停/恢复由执行器负责）。
5. **严格 1 Task : 1 Workflow**：每个任务**唯一对应**一个工作流定义与文档（与 `docs/tasks`、`docs/tasks/workflows` 对齐）。
6. **工作流步骤**：按编码、测试、复核等规范逐步执行（以 `docs/specs` 为准）。
7. **交付流水线**：**检查（Check）→ 合并（Merge）→ 构建（Build）→ 清理冗余文件（Clean）**。
8. **输出与结案**：将**产物**提交用户确认（Review / Output）；与本轮 **`session_id`** 一致的会话索引及（可选）归档目录落在 `docs/sessions` 等约定位置。

## 迭代环节（切面）

### 定义

**迭代环节**不替代拼图或执行的主干，而是**插入**两者运行过程与**每次 Session 的边界**上：对失败做推理与审计并形成可消费的反馈；对成功将已通过验证的工作流**沉淀为可复用资产**并维护**排行榜**；且**无论成功还是失败**都应进行**知识蒸馏**，产出写入可追溯存储，供**下一轮**拼图或执行使用。

### 本项目的核心执行逻辑

1. **挂钩执行主权**：审计、蒸馏与资产沉淀所针对的**那一轮交付**，在文档与存储上与执行环节已确立的 **`session_id`** 对齐（载体见 [sessions.md](./sessions/sessions.md)），避免与「尚未进入执行」的拼图材料混淆。
2. **失败路径**：任务或工作流失败 → **推理 / 审计** → 形成**新反馈** → 可**回流拼图**（改需求/门控）或**指导执行纠偏**。
3. **成功路径**：已通过验证的工作流 → **正式化为资产** → **排行榜**鼓励后续优先采用。
4. **知识蒸馏**：与上两条**并列约束**——单次 Session **无论成败**都应蒸馏；具体落点与 `docs/procedure/distillation`、`docs/sessions` 对齐。

## 关系摘要（两个循环一个切面）

| 环节         | 与执行是否对齐                    | 典型产物                           |
| ------------ | --------------------------------- | ---------------------------------- |
| 拼图（循环） | **不对齐**；异步                  | 需求、里程碑、先决条件、结构化反馈 |
| 执行（循环） | 对齐任务与工作流                  | 任务、工作流、构建与清理后的产物   |
| 迭代（切面） | 横切拼图与执行；挂靠 Session 边界 | 审计结论、资产、排行榜项、蒸馏知识 |
