# Design Defect Analysis for dp-ring

## Context

Analysis of the Adaptive Flywheel design based on a full reading of all project documents, the drawio prototype, existing code, CLI tools, and formalized workflows.

---

## Identified Defects

### Defect 1: "Evolution" Has No Defined Mechanism — It's Aspirational, Not Operational

**Where**: `core-logic.md`, `VALUE.md`, `docs/procedure/evolution/`

The entire system is premised on "each session performing better than the previous one," but there is **no concrete mechanism** that makes this happen. The documents say knowledge distillation occurs and assets are formalized, but:

- There is no definition of **what "better" means** (no quality metrics, no scoring, no comparison baseline).
- The "leaderboard" (`资产与排行榜`) is mentioned repeatedly but has **zero specification** — what is ranked, by what criteria, how rankings influence future workflow selection.
- Knowledge distillation writes to `docs/procedure/distillation/`, but there is **no specification of what a distillation artifact contains**, how it is consumed by the next session, or how an agent would actually use it to improve.
- The Evolution boxes in the drawio feed **back into** the Feedback layer, but the mechanism is just an arrow — there's no protocol for how evolution outputs become actionable inputs.

**Impact**: The flywheel doesn't actually fly. Without measurable improvement criteria, the system is a documentation framework, not an adaptive system.

---

### Defect 2: The "Iteration Aspect" Is Not Actually an Aspect — It's a Sequential Phase Pretending to Be Cross-Cutting

**Where**: `core-logic.md` §迭代环节

The document insists iteration is an "aspect" (切面) that cross-cuts puzzle and execution. But examining the actual flow:

1. Failure reasoning happens **after** execution fails.
2. Asset formalization happens **after** execution succeeds.
3. Knowledge distillation happens **at session boundaries**.

All three are **sequential post-processing steps**, not cross-cutting concerns. A true aspect would intercept **during** execution (e.g., monitoring code quality in real-time, detecting drift mid-workflow). The current design is just a post-mortem phase with a misleading name.

**Impact**: Mislabeling creates confusion about when iteration activities can and should occur. It prevents the design from evolving toward genuine mid-execution learning (which would be far more valuable for agent improvement).

---

### Defect 3: Puzzle-Execution Boundary Is Over-Engineered for a Single-Agent Scenario

**Where**: `core-logic.md`, gate control logic

The gate control system (milestones must be valid, all prerequisites satisfied, documentation consistent) is designed for a multi-team, multi-agent orchestration where one team does analysis and another does implementation. But:

- The current system has **one requirement** (`r1`), **one task** (`t1`), **one workflow** (`t1w1`), and **one session**.
- The gate is described as a hard barrier, but there's no mechanism to **evaluate** whether prerequisites are actually satisfied — it's a human judgment written in markdown.
- There's no state machine implementation or even a schema for gate status transitions.

**Impact**: The formalism creates ceremony without value at this stage. It also doesn't scale — when you have 50 requirements with interdependent prerequisites, you need programmatic gate evaluation, not markdown checkboxes.

---

### Defect 4: No Quality Measurement System at Any Level

**Where**: System-wide absence

The system mentions "review" (复核), "check" (检查), and "leaderboard" (排行榜) but defines **none of them operationally**:

- **Workflow quality**: No metrics. What makes Workflow A better than Workflow B?
- **Output quality**: No definition. "User confirms" is the only acceptance criterion.
- **Agent performance**: No tracking. Which agent configurations produce better results? Unknown.
- **Knowledge quality**: Distilled knowledge has no validity measure. Bad distillation propagates to all future sessions.

This is the most critical gap if the goal is evolution. Without measurement, there is no selection pressure, and without selection pressure, there is no evolution.

---

### Defect 5: Session Management Conflates Traceability with Lifecycle

**Where**: `sessions.md`, `core-logic.md` §session_id

`session_id` is defined as a traceability key (linking tasks, workflows, outputs, archives). But it's also implicitly expected to carry lifecycle semantics:

- When does a session start? "When gate control passes."
- When does it end? "When closure and archiving happen."
- What happens if a session is partially complete and needs to be resumed across multiple human interactions? Undefined.
- What about sessions that span multiple days, multiple agents, or multiple context windows? No protocol.

For the stated goal (agent development workflow), sessions are where the rubber meets the road. The current definition is too tied to document archiving and not enough to operational lifecycle management.

---

### Defect 6: The 1:1 Task-Workflow Constraint Is Unnecessarily Rigid

**Where**: `core-logic.md` §执行环节 rule 5

"Every task uniquely corresponds to one workflow definition and document." This means:

- You cannot reuse a proven workflow across multiple tasks without duplicating it.
- You cannot compose workflows from shared sub-workflows.
- The "formalized asset" workflows in `docs/assets/formalized_workflow/` are reference documents, not executable templates that can be bound to new tasks.

This directly contradicts the evolution goal. If a workflow proves effective, the system should make it **easier** to reuse, not require a fresh copy for each task.

---

### Defect 7: Parallel/Serial Choice Is Mandated but Supervision Is Unspecified

**Where**: `core-logic.md` §执行环节 rule 4, `backend-modules.md` modules 7-8

The design mandates explicit parallel/serial task selection with:
- Parallel: Supervisor + conflict escalation to human
- Serial: Queue with backpressure

But there's no specification of:
- What "conflict" means in concrete terms (file-level? semantic? resource?)
- How the supervisor detects conflicts
- What "agent suggestion + human decision" looks like in practice
- How backpressure/pause/resume works

This is a policy mandate without implementation guidance. An agent reading these docs would know it **must** choose parallel or serial but would have **no idea how** to implement either correctly.

---

### Defect 8: Documentation-Driven Approach Creates a Bootstrapping Problem for Agents

**Where**: System-wide

The entire system is "documentation-driven" — agents read markdown to understand what to do, write markdown as output, and use markdown documents as state machines. But:

- **Agents cannot reliably parse the document conventions**. The naming rules, cross-references, `session_id` three-part format, and CLI tool dependencies form a complex protocol that even a capable agent would struggle with.
- **The document structure is self-referential to a degree that creates circular dependencies**. For example: to create a document you need the CLI, which needs naming rules from `documentation-standards.md`, which references `sessions.md` for session IDs, which references `coding-standards.md` for code imports, which references back to `documentation-standards.md`.
- **There's no machine-readable schema**. Everything is in Markdown prose. An agent that needs to check "are all prerequisites satisfied?" must parse free-text markdown tables, not query a structured data source.

**Impact**: The system that's supposed to help less-intelligent agents work effectively requires a high baseline intelligence just to navigate its documentation.

---

### Defect 9: Feedback Loop Has No Prioritization or Triage

**Where**: `docs/feedbacks/Feedback.md`, `core-logic.md` §拼图

Feedback from failed sessions flows back to the puzzle phase, but:

- There's no severity/priority classification for feedback.
- There's no mechanism to distinguish "this feedback invalidates the requirement" from "this is a minor implementation note."
- Multiple feedback items from multiple sessions could conflict with each other — no resolution protocol exists.
- The "trigger" that awakens the puzzle phase is defined as "existence of valid feedback that can form new requirements or narrow ambiguity" — but "valid" is undefined.

---

### Defect 10: The Frontend Is Structurally Disconnected from the System It Describes

**Where**: `src/`, `package.json`

The frontend is a blank Vite+React app. The docs describe a complex orchestration system. There's no path from one to the other:

- No API contracts defined (REST, GraphQL, WebSocket — all listed as "to be completed")
- No event schema
- No domain model in code
- The frontend doesn't even display the documentation structure it sits alongside

This isn't necessarily a defect in the design itself, but it means the **only working part** of the system is the CLI tooling for generating document names and markdown templates. The "product" is currently a documentation specification, not software.

---

## Summary: Root Cause

Most of these defects trace to a single root cause: **the system specifies structure and process without specifying outcome criteria or computational mechanisms**. It's a comprehensive _taxonomy_ of what an adaptive agent development workflow should contain, but it lacks the _algebra_ — the rules that transform inputs into measurably better outputs.

The flywheel metaphor implies momentum (each cycle adds energy), but the current design has no energy source defined. Knowledge distillation, formalization, and evolution are named but not operationalized.

# Redesign Proposal

## Design Decisions (User-Confirmed)

- **System role**: Both — a protocol layer any tool can follow + an optional orchestrator on top.
- **State storage**: Repo as authoritative source (structured files in git), optional DB/service as index/cache.

---

## 1. Design Principles

### 1.1 Schema-First, Prose-Second

Every artifact in the system (requirement, milestone, task, workflow, session, feedback, evaluation, distillation) is defined by a **JSON Schema**. The schema is the contract. Markdown documents become **human-readable views** generated from or annotated onto the structured data — not the source of truth.

```
.ring/                          # machine-readable state (git-tracked)
  schemas/                      # JSON Schema definitions for every artifact type
  sessions/                     # session lifecycle records (JSON)
  requirements/                 # structured requirement records
  tasks/                        # task records
  workflows/                    # workflow definitions (reusable templates)
  workflow-runs/                # per-task workflow execution records
  evaluations/                  # scoring records
  registry/                     # leaderboard & asset index
  feedback/                     # structured feedback items
  distillations/                # knowledge artifacts
docs/                           # human-readable layer (can be auto-generated from .ring/)
```

**Why `.ring/`**: Separates machine state from human docs. Agents read `.ring/`. Humans read `docs/`. A build step can sync one to the other. Git tracks both — full audit trail.

### 1.2 Everything Has a Typed Envelope

Every artifact file in `.ring/` shares a common envelope:

```jsonc
{
  "$schema": "./schemas/<type>.schema.json",
  "id": "<unique-id>",
  "type": "<artifact-type>",
  "version": 1,                    // monotonic, incremented on mutation
  "created_at": "ISO-8601",
  "updated_at": "ISO-8601",
  "created_by": "<agent-id | human>",
  "session_id": "<session-id | null>",  // null for puzzle-phase artifacts
  "status": "<type-specific-status>",
  "data": { /* type-specific payload */ }
}
```

Agents never need to parse prose. They read JSON, validate against schema, write JSON. The protocol layer validates every write against the schema before accepting it.

### 1.3 State Machines Are Explicit

Every artifact type with a lifecycle (session, task, requirement, workflow-run) defines its **allowed state transitions** in its schema:

```jsonc
// In session.schema.json
"status": {
  "enum": ["gate_pending", "preparing", "executing", "reviewing", "closing", "closed", "failed"],
  "x-transitions": {
    "gate_pending": ["preparing", "failed"],
    "preparing": ["executing", "failed"],
    "executing": ["reviewing", "failed"],
    "reviewing": ["closing", "executing"],  // can loop back
    "closing": ["closed"],
    "failed": ["gate_pending"]              // retry goes back to start
  }
}
```

An agent or orchestrator that attempts an invalid transition gets a schema validation error. No ambiguity.

## 2. Quality Measurement Framework

This is the core missing piece. Without it, no evolution.

### 2.1 Dimensions

Quality is measured across **five dimensions**, each producing a score in `[0.0, 1.0]`:

| Dimension | What It Measures | How It's Computed |
|---|---|---|
| **Correctness** | Does output match specification? | Automated checks (tests pass, build succeeds, lint clean) + structured human assessment |
| **Completeness** | Are all requirements/acceptance criteria addressed? | Checklist coverage: `satisfied_criteria / total_criteria` |
| **Efficiency** | Resource cost to reach the goal | Normalized inverse of: token count, wall-clock time, retry count, human intervention count |
| **Adherence** | Did the agent follow the protocol? | Schema validation pass rate, state transition validity, naming convention compliance |
| **Reusability** | How much of this session's work benefits future sessions? | Count of artifacts formalized as reusable assets, weighted by subsequent usage |

### 2.2 Evaluation Record

After every session (success or failure), an evaluation record is created:

```jsonc
// .ring/evaluations/eval-<session_id>.json
{
  "$schema": "./schemas/evaluation.schema.json",
  "id": "eval-s3-feature-abc-x9k2m420260408",
  "session_id": "s3-feature-abc-x9k2m420260408",
  "outcome": "success",          // or "failure" or "partial"
  "scores": {
    "correctness": 0.95,
    "completeness": 0.80,
    "efficiency": 0.60,
    "adherence": 1.0,
    "reusability": 0.40
  },
  "composite_score": 0.75,       // weighted aggregate
  "score_weights": { "correctness": 0.30, "completeness": 0.25, "efficiency": 0.20, "adherence": 0.15, "reusability": 0.10 },
  "evidence": {
    "tests_passed": 42,
    "tests_failed": 0,
    "build_status": "success",
    "lint_errors": 0,
    "criteria_satisfied": ["c1", "c2", "c3", "c4"],
    "criteria_unsatisfied": ["c5"],
    "total_tokens": 128000,
    "wall_clock_seconds": 3600,
    "retry_count": 1,
    "human_interventions": 2,
    "assets_formalized": ["wf-template-react-component"]
  },
  "evaluator": "human",          // or "automated" or "hybrid"
  "notes": "..."                  // free-text, optional
}
```

### 2.3 Score Weights Are Configurable and Evolvable

The `score_weights` are stored in `.ring/config.json` and can themselves evolve — if the team decides correctness matters more, they change the weights. The leaderboard re-ranks accordingly.

## 3. Evolution Mechanism

Evolution requires four things: **variation, evaluation, selection, and inheritance**. Here's how each maps to the system:

### 3.1 Variation: Workflow Templates + Strategy Registry

Workflows are no longer 1:1 with tasks. Instead:

- **Workflow Templates** (`.ring/workflows/`) are reusable, parameterized definitions. They describe steps, expected inputs/outputs, and applicable task types.
- **Workflow Runs** (`.ring/workflow-runs/`) are instances — a specific execution of a template against a specific task in a specific session.
- A task **selects** a workflow template (or the orchestrator selects one for it). Multiple tasks can use the same template. The same task type can be tried with different templates across sessions.

```jsonc
// .ring/workflows/wf-react-component.json
{
  "id": "wf-react-component",
  "name": "React Component Development",
  "version": 3,
  "applicable_to": ["feature-implementation", "bug-fix"],
  "steps": [
    { "id": "s1", "name": "analyze", "type": "analysis", "inputs": ["requirement"], "outputs": ["design-spec"] },
    { "id": "s2", "name": "implement", "type": "coding", "inputs": ["design-spec"], "outputs": ["code-diff"] },
    { "id": "s3", "name": "test", "type": "testing", "inputs": ["code-diff"], "outputs": ["test-report"] },
    { "id": "s4", "name": "review", "type": "review", "inputs": ["code-diff", "test-report"], "outputs": ["review-verdict"] }
  ],
  "quality_history": {
    "usage_count": 12,
    "avg_composite_score": 0.78,
    "last_5_scores": [0.82, 0.75, 0.80, 0.71, 0.85]
  }
}
```

### 3.2 Evaluation: Automatic + Human Hybrid

After each session/workflow-run:

1. **Automated evaluation** runs first: test results, build status, lint, schema compliance, token/time metrics.
2. **Human evaluation** supplements: acceptance criteria checklist, subjective quality notes.
3. Both are merged into the evaluation record (section 2.2 above).

### 3.3 Selection: Registry-Driven Dispatch

The **registry** (`.ring/registry/leaderboard.json`) ranks workflow templates by composite score for each task type:

```jsonc
{
  "rankings": {
    "feature-implementation": [
      { "workflow_id": "wf-react-component", "avg_score": 0.78, "usage_count": 12 },
      { "workflow_id": "wf-tdd-first", "avg_score": 0.72, "usage_count": 5 },
      { "workflow_id": "wf-spike-then-refine", "avg_score": 0.65, "usage_count": 3 }
    ],
    "bug-fix": [ ... ]
  }
}
```

When a new task arrives, the dispatch step queries the registry:
- **Default**: use the top-ranked workflow for this task type.
- **Explore**: occasionally use a lower-ranked or new workflow to gather data (explore-exploit tradeoff).
- **Human override**: the user can always pick a specific workflow.

This is the **selection pressure**. Better workflows get more usage. Worse ones get less.

### 3.4 Inheritance: Knowledge Distillation as Structured Artifacts

Distillation is no longer "write something to a directory." It produces **typed knowledge artifacts**:

```jsonc
// .ring/distillations/dist-<session_id>.json
{
  "id": "dist-s3-feature-abc-x9k2m420260408",
  "session_id": "s3-feature-abc-x9k2m420260408",
  "type": "distillation",
  "artifacts": [
    {
      "kind": "lesson",              // or "pattern", "anti-pattern", "tool-config", "prompt-template"
      "summary": "React 19 useTransition requires wrapping state updates in startTransition",
      "context": "feature-implementation",
      "applicable_when": "Using React 19 concurrent features",
      "confidence": 0.9,             // 1.0 = verified across multiple sessions
      "source_sessions": ["s3-feature-abc-x9k2m420260408"]
    },
    {
      "kind": "anti-pattern",
      "summary": "Do not run lint before tests — test failures are more actionable",
      "context": "workflow-ordering",
      "applicable_when": "Defining step order in any workflow",
      "confidence": 0.7,
      "source_sessions": ["s3-feature-abc-x9k2m420260408"]
    }
  ]
}
```

At session start, the agent (or orchestrator) **queries distillations** relevant to the current task type and injects them as context. This is how knowledge propagates. Confidence scores increase when multiple sessions reinforce the same lesson; they decrease (or items get archived) when contradicted.

### 3.5 The Flywheel in Action

```
Session N starts
  → Query registry → select top workflow for task type
  → Query distillations → inject relevant lessons as context
  → Execute workflow steps
  → Evaluate (automated + human)
  → Score → update registry rankings
  → Distill → extract lessons/patterns
  → Update workflow template quality_history
Session N+1 starts with better defaults and more knowledge
```

This is the concrete mechanism for "each session performs better than the previous one."

## 4. Session Lifecycle

Sessions get a proper state machine, not just a traceability key.

### 4.1 States

```
               ┌──────────────────────────────────────────┐
               │                                          │
gate_pending → preparing → executing → reviewing → closing → closed
     │              │           │           │
     └──────────────┴───────────┴───────────┴──→ failed
                                                    │
                                                    └──→ gate_pending (retry)
```

### 4.2 Session Record

```jsonc
// .ring/sessions/s3-feature-abc-x9k2m420260408.json
{
  "id": "s3-feature-abc-x9k2m420260408",
  "status": "executing",
  "requirement_id": "r2-dashboard-feature",
  "milestone_id": "r2m1-basic-layout",
  "task_ids": ["t5-implement-sidebar"],
  "workflow_run_ids": ["run-t5-wf-react-component"],
  "started_at": "2026-04-08T10:00:00Z",
  "updated_at": "2026-04-08T12:30:00Z",
  "ended_at": null,
  "evaluation_id": null,                      // set on close
  "distillation_id": null,                    // set on close
  "context_injected": {
    "workflow_template": "wf-react-component",
    "distillations_applied": ["dist-s1-...", "dist-s2-..."],
    "registry_rank_at_selection": 1
  },
  "execution_log": [
    { "timestamp": "...", "event": "status_transition", "from": "gate_pending", "to": "preparing", "actor": "human" },
    { "timestamp": "...", "event": "status_transition", "from": "preparing", "to": "executing", "actor": "orchestrator" },
    { "timestamp": "...", "event": "step_completed", "step": "s1-analyze", "duration_sec": 300 },
    { "timestamp": "...", "event": "step_completed", "step": "s2-implement", "duration_sec": 1800 }
  ]
}
```

### 4.3 Multi-Day/Multi-Agent Sessions

The session record persists in the repo. Any agent can read it, check the current status, and continue from the last completed step. The `execution_log` provides continuity. No need for a single agent to hold everything in memory.

## 5. Gate Control — Programmatic, Not Prose

### 5.1 Prerequisites as Machine-Evaluable Conditions

```jsonc
// Inside a milestone record
"prerequisites": [
  {
    "id": "pre-1",
    "description": "Build passes",
    "type": "automated",
    "check": { "command": "npm run build", "expect_exit_code": 0 },
    "status": "satisfied",
    "last_checked": "2026-04-08T09:00:00Z"
  },
  {
    "id": "pre-2",
    "description": "Design spec approved",
    "type": "human",
    "check": { "requires": "human_approval", "approver_role": "lead" },
    "status": "unsatisfied",
    "last_checked": null
  },
  {
    "id": "pre-3",
    "description": "Dependency task t3 completed",
    "type": "reference",
    "check": { "artifact": ".ring/tasks/t3-setup-auth.json", "field": "status", "equals": "completed" },
    "status": "satisfied",
    "last_checked": "2026-04-08T08:30:00Z"
  }
]
```

Gate evaluation: iterate prerequisites, run checks, all must be `"satisfied"`. Agents or the orchestrator can run this programmatically. No markdown parsing.

## 6. Feedback with Triage

```jsonc
// .ring/feedback/fb-<id>.json
{
  "id": "fb-001",
  "source_session_id": "s2-...",
  "severity": "critical",            // critical | major | minor | info
  "category": "requirement_gap",     // requirement_gap | implementation_bug | workflow_flaw | tooling_issue
  "target": {
    "type": "requirement",
    "id": "r2-dashboard-feature",
    "field": "acceptance_criteria[3]"
  },
  "description": "Acceptance criterion 3 assumes an API endpoint that doesn't exist yet",
  "proposed_action": "Add prerequisite: API endpoint /api/sidebar must be implemented",
  "status": "open",                   // open | acknowledged | resolved | wont_fix
  "resolution_session_id": null
}
```

The puzzle phase queries feedback by severity and status. `critical` items block gate passage. `major` items must be acknowledged before proceeding. This is the triage mechanism.

## 7. Agent Interface Contract

This is how the system becomes agent-friendly. Agents don't need to understand the full system — they need to know **what to read, what to write, and what shape the data must be**.

### 7.1 Session Startup Protocol (What an Agent Reads)

When an agent starts a session, it reads **exactly these files** in order:

1. `.ring/sessions/<session_id>.json` — current status, what task, what milestone
2. `.ring/tasks/<task_id>.json` — what to do, acceptance criteria
3. `.ring/workflows/<workflow_id>.json` — how to do it (steps)
4. `.ring/workflow-runs/<run_id>.json` — current progress (which steps done)
5. `.ring/distillations/` — filtered by `context` matching current task type
6. `.ring/feedback/` — filtered by `target.id` matching current requirement, `status: open`

That's it. Six reads. All JSON. All schema-validated.

### 7.2 Session Execution Protocol (What an Agent Writes)

During execution, the agent writes:

1. **Step outputs** → append to workflow-run record
2. **Status transitions** → update session record (validated against state machine)
3. **Code changes** → normal git operations
4. **Issues encountered** → create feedback records

### 7.3 Session Closure Protocol (What Happens After)

1. Automated evaluation runs → creates evaluation record
2. Human reviews evaluation, adds human scores → updates evaluation record
3. Distillation runs → creates distillation record
4. Registry updates → recalculates leaderboard rankings
5. Session status → `closed`

### 7.4 Minimal Agent Requirements

An agent that participates in this system needs only:
- Read JSON files
- Write JSON files that validate against provided schemas
- Execute shell commands (for the actual work: code, test, build)
- Follow a linear step sequence from the workflow definition

No need to understand markdown conventions, naming rules, cross-references, or CLI tools. The protocol is the interface.

## 8. Addressing Each Original Defect

| # | Defect | Resolution |
|---|---|---|
| 1 | Evolution has no mechanism | §3: Variation (templates) + Evaluation (scoring) + Selection (registry) + Inheritance (distillation) |
| 2 | No quality measurement | §2: Five-dimension scoring framework with automated + human hybrid evaluation |
| 3 | "Aspect" is actually sequential | Renamed: the post-session evaluation/distillation is now explicitly a **closure protocol** (§7.3), not a cross-cutting aspect. Mid-execution monitoring can be added later as actual middleware in workflow steps |
| 4 | Bootstrapping problem | §7: Agent interface contract. Six JSON reads to start. Schema validation for writes. No prose parsing required |
| 5 | Session conflates traceability/lifecycle | §4: Explicit state machine, multi-day support via persistent session records, structured execution log |
| 6 | 1:1 Task-Workflow is rigid | §3.1: Workflow templates are reusable. Tasks reference templates. Workflow-runs are per-execution instances |
| 7 | Gate has no programmatic evaluation | §5: Prerequisites as machine-evaluable conditions (command checks, reference checks, human approval flags) |
| 8 | Parallel/serial unspecified | Deferred to orchestrator layer. The protocol layer defines tasks and dependencies. The orchestrator decides scheduling. Conflict = same file modified by concurrent workflow-runs (detectable via git) |
| 9 | Feedback has no triage | §6: Severity levels, categories, and status tracking. Critical blocks gates |
| 10 | Frontend disconnected | Out of scope for this design. But with `.ring/` as structured data, a frontend becomes a straightforward viewer/editor of JSON records. API is "read/write files" or the optional DB cache |

## 9. Key Design Decisions Still Open

These need your input before implementation:

1. **Score weight defaults**: The proposed weights (correctness 0.30, completeness 0.25, efficiency 0.20, adherence 0.15, reusability 0.10) — do these match your priorities?

2. **Explore-exploit ratio**: When dispatching workflows, how often should the system try a non-top-ranked workflow? 10%? 20%? User-configured?

3. **Distillation confidence decay**: Should confidence scores on knowledge artifacts decay over time if not reinforced? This prevents stale lessons from dominating.

4. **Schema versioning**: When schemas evolve, how should existing records be migrated? In-place migration scripts, or version-tagged schemas with backward-compatible reads?

5. **Evaluation automation boundary**: Which of the five dimensions can be fully automated today vs. requiring human input? Correctness and adherence are mostly automatable. Completeness, efficiency, reusability likely need hybrid assessment initially.
